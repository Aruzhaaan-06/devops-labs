API мекенжайы осы жұмыс ортасында `http://localhost:8088/`; 8080 порты бұрыннан басқа қызметке тиесілі.

Одан кейін [PR #18](https://github.com/Aruzhaaan-06/devops-labs/pull/18) арқылы GET / жауабына `message: "hello from CI/CD"` қосылды. Бұрынғы service, version және host өрістері сақталды. APP_VERSION конфигурациясы мен жаңа өріске арналған интеграциялық тест қосылды. InMemory-де 39 тест өтті; GitHub-hosted PostgreSQL CI-де де жаңа тест орындалды. Жаңа main коды `349a0b1` болды, контейнердегі нұсқа - `sha-349a0b1`.

## Артефакт және орналастыру

Образ: `ghcr.io/aruzhaaan-06/devops-labs`. `image` job оны GitHub-hosted Ubuntu-да құрастырып, `sha-<main қысқа SHA>` және `latest` тегтерімен жариялайды. Deploy `latest` арқылы емес, нақты sha-тег арқылы жасалады. `API_IMAGE` және `API_TAG` jobs outputs арқылы беріледі; бөлек runner-лердің дискілері ортақ емес.

Жергілікті self-hosted Windows runner дайын образды жүктейді. `docker compose up -d --no-build --wait --wait-timeout 90` құрастыру жасамайды және healthy күйін күтеді. Кейін `/health/ready` тексеріледі. Жаңа Job summary қадамы GET / нұсқасын сұралған API_TAG мәнімен салыстырып, тексерілген образды көрсетеді.

`sha-*` тегі бастапқы код коммитін көрсетеді; Docker тегі registry саясаты болмаса техникалық тұрғыдан қайта тағайындалуы мүмкін. Сондықтан нақты іске қосылған image ID және registry digest дәлелдерде бөлек сақталады. Тег атының өзі криптографиялық өзгермейтін артефакт деп көрсетілмейді.

## Қайта орындау және екі кері қайтару

Бірдей тегке deploy қайта орындалғанда API контейнерінің ID-і мен StartedAt мәні салыстырылады. Олардың бірдей болуы контейнердің қайта жасалмағанын растайды.

Қолмен кері қайтару бұрынғы `sha-8511c6c` образына жасалады. Уақыт бірінші Compose пәрменінен бастап GET / ескі version мәнін растаған сәтке дейін өлшенеді. Осы кезде message өрісі болмайды. Код ауысады, бірақ `devops-labs_pgdata` томы жойылмайды; алдын ала жасалған жоба мен тапсырма дәл салыстырылады. Қолмен кері қайтарутан кейін ағымдағы main пайплайны Re-run all jobs арқылы қайтарылады.

Қосымша `workflow_dispatch` оқиғасы `tag` мәнін қабылдап, бөлек rollback job-ты іске қосады. Бұл оқиғада test/image/deploy өткізіледі; бұрынғы образ қайта құрастырылмайды. Tag тек env арқылы беріледі және Docker пәрмендеріне дейін `sha-xxxxxxx` немесе `x.y.z` пішімімен тексеріледі. `latest` қабылданбайды. Release тегінің APP_VERSION мәні оның атына тең болмауы мүмкін, сондықтан rollback нақты таңдалған образдың APP_VERSION мәнін тексереді.

Батырмалық сценарийдің уақыты dispatch сұрауынан ескі нұсқаны бірінші растауға дейін есептеледі; оған approval, кезек және бақылау аралығы кіреді. Бұл көрсеткіш тікелей Compose пәрменінің уақытымен бірдей өлшем емес.

## Environment local және құпия дерек

Deploy пен rollback `local` Environment-іне байланған. Required reviewer - репозиторий иесі; тек protected branches рұқсат етілген. Құпиясөз бұрыннан бар DB_PASSWORD repository secret-інен беріледі. Мән есепке не Git-ке жазылмайды. Deploy/rollback күтуі API арқылы дәлелденіп, осы нақты оқу сценарийлері үшін иенің тапсырмасы бойынша мақұлданады. Бұл тәуелсіз адамның қосымша мақұлдауы ретінде көрсетілмейді.

Main және қолмен іске қосылған workflow-лар бір ref бойынша кезекпен орындалады, жаңа push олардың deploy-ын жарты жолда тоқтатпайды. PR тексерулерінде ғана cancel-in-progress сақталған. Қоғамдық репозиторийдегі self-hosted runner sandbox емес; сыртқы қатысушыларға all_external_contributors мақұлдауы бұрынғыдай міндетті.

## Релиз

v1.0.0 тегі image job-та `1.0.0` registry тегін жасайды. Тег оқиғасы deploy немесе rollback жасамайды; нақты контейнер ID/StartedAt пен нұсқа салыстырылып тексеріледі. Автоматты release notes және осы жұмыстың есебі GitHub Release бетінде жарияланады.

Есеп жарияланған кейінгі құжат коммиті main-нің жаңа SHA-ын алады. Сондықтан PDF-тегі нұсқа суреттері сол өлшеу сәтіндегі main-ге қатысты; түпкілікті main мен тірі API сәйкестігі release-ке тіркелетін `lab10-final-verification.json` арқылы беріледі. Бұл өз SHA-ын ішіне жазуға тиіс PDF коммитінің тұйық тәуелділігін болдырмайды.

## Дәріс сұрақтарына жауап

1. **PR кезінде образ неге жіберілмейді?** Ол әлі қабылданбаған код; PR үшін жинау мен тест жеткілікті. Package write құқығы және жергілікті deploy тек тексерілген main/tag жолында беріледі.
2. **CI PostgreSQL-і мен конфигурациясы қайдан алынады?** `services.postgres` уақытша контейнер береді, health check дайындықты күтеді; Storage және ConnectionStrings__Db ортасы SQL режимін таңдайды.
3. **sha-тег latest-тен несімен пайдалы?** Ол кодтың нақты коммитін көрсетіп, бұрынғы нұсқаны таңдауға мүмкіндік береді. Дәл артефакт үшін digest те сақталады; latest жылжып отырады.
4. **NAT артындағы runner қалай қосылады?** Runner GitHub-қа өзі шығыс HTTPS қосылымын орнатып, тапсырма күтеді. Компьютерге сырттан ашық порт қажет емес.
5. **Қайта құрастырмай қалай қайтамыз?** Бұрын жарияланған және жергілікті кэште бар образды таңдап, Compose up --no-build --wait орындаймыз; соңында нұсқа мен readiness тексеріледі.
6. **image-ден deploy-ға дерек қалай беріледі?** Step outputs → job outputs → needs.image.outputs арқылы беріледі. Жай файл жеткіліксіз: jobs бөлек компьютерлерде орындалады.
7. **Delivery және Deployment айырмасы?** Delivery дайын артефакт береді, іске қосуды бөлек шешім басқарады; Deployment іске қосуды да орындайды. Осы нұсқада main deploy-ы local approval күтеді, тег тек образ шығарады.
8. **Сол тегті қайта deploy етсек не болады?** Compose конфигурациясы мен образ өзгермесе, контейнер сол қалпында қалады. Бұл жұмыс контейнер ID және StartedAt арқылы тексерді.

Формалды шектеулер бұрынғыдай: екі аккаунт бір иеге тиесілі, оқытушы логині берілмеген. Бұл жұмыс басқа студентпен тәуелсіз жұптық жұмысты дәлелдемейді.
