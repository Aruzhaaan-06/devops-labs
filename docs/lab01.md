## Часть 1: запросы и ошибки

Откройте коллекцию `demo-api` из `postman/demo-api.postman_collection.json`. Создайте проект, сохраните возвращённый id, затем задачу в этом проекте. Идентификаторы между запусками и проверками различаются.

| Запрос | Ожидаемый результат |
|---|---|
| `GET /api/projects` после запуска нового InMemory-процесса | 200, `[]` |
| `POST /api/projects`, `{"name":"Курс DevOps"}` | 201, проект, `Location` |
| `POST /api/tasks`, `{"projectId":<id>,"title":"Написать Dockerfile"}` | 201, новая задача в Todo |
| `GET /api/tasks?projectId=<id>` | 200, задачи проекта |
| `PATCH /api/tasks/<id>/status`, `{"status":"InProgress"}` | 200, обновлённая задача |
| `GET /api/projects/<id>` | 200, проект |
| Пустое имя проекта | 400, сведения о поле в `errors` |
| Повторное имя проекта | 409, `detail`: `Проект «<имя>» уже существует` |
| Новая Todo-задача сразу в Done | 409, `detail`: `Нельзя перевести задачу <id> из Todo в Done` |
| Несуществующая задача | 404 |

Точный текст `errors` нужно брать из фактического ответа валидатора. Не следует заменять его предполагаемой формулировкой. Для проверки перехода Todo → Done создайте отдельную задачу: задача из успешного PATCH уже находится в InProgress.

`InMemoryStore` содержит списки проектов и задач и зарегистрирован singleton. Он живёт весь срок одного процесса и общий для запросов этого процесса; завершение приложения уничтожает данные. После Shift+F5 и нового F5 создаётся новое пустое хранилище. Реальный перезапуск процесса проверен: `evidence/lab01/restart/before.json` содержит4 проекта, `after.json` — ответ200 и `[]`. Эта проверка не означает, что перезапуск выполнялся клавишами Visual Studio. Постоянное хранение требует SQL-режима, который проверяется в следующей части курса.

## Часть 2: две цепочки вызовов

Установите F9 в `TasksController.ChangeStatus`, `TaskService.GetAsync`, `TaskService.ChangeStatusAsync`, `InMemoryTaskRepository.GetAsync` и `SetStatusAsync`. Используйте F10 для следующей строки, F11 для входа в метод; наблюдайте Locals и Call Stack. Ниже описан путь по актуальному коду; ручное выполнение этих шагов и скриншоты Locals/Call Stack пока отсутствуют. Захват интерфейса завершился тайм-аутом. Цепочки проверены чтением исходников, соответствующие ответы200/409 — реальными HTTP-запросами; это не заменяет наблюдение отладчиком.

### Todo → Done: 409

```text
TasksController.ChangeStatus
  → TaskService.GetAsync
  → InMemoryTaskRepository.GetAsync
  → возврат найденной Todo-задачи в контроллер
  → StatusRules.CanTransition(Todo, Done): false
  → return Problem(..., statusCode: StatusCodes.Status409Conflict)
```

HTTP-код выбирает `TasksController.ChangeStatus` в ветке запрещённого перехода. Обновление не вызывается: `TaskService.ChangeStatusAsync` и `InMemoryTaskRepository.SetStatusAsync` не достигаются; задача остаётся Todo.

### Todo → InProgress: 200

```text
TasksController.ChangeStatus
  → TaskService.GetAsync
  → InMemoryTaskRepository.GetAsync
  → StatusRules.CanTransition(Todo, InProgress): true
  → TaskService.ChangeStatusAsync
  → InMemoryTaskRepository.SetStatusAsync
  → InMemoryTaskRepository.Replace
  → возврат обновлённой задачи в сервис, затем контроллер
  → return updated: HTTP 200
```

`Replace` заменяет неизменяемую запись копией с новым Status и UpdatedAt под `lock (store.Sync)`. В контроллере `return updated` формирует 200 с JSON; если обновление вернуло null, предшествующая ветка формирует 404. Для запрещённого запроса сохраните Locals с `task.Status=Todo`, для успешного — стек и значения при записи нового статуса. Номера строк нужно сверять по версии файлов, включённой в сдачу.

## Шесть ответов по коду

1. **Маршрут `api/tasks/{id}/status`.** В `Controllers/TasksController.cs`: `[Route("api/tasks")]` на классе и `[HttpPatch("{id:int}/status")]` над `ChangeStatus`. Атрибуты задают HTTP-метод PATCH и ограничивают id целым числом.
2. **400 при пустом title.** `[ApiController]` запускает автоматическую проверку модели до действия; `CreateTaskRequest.Title` и `UpdateTaskRequest.Title` имеют `[Required, StringLength(200)]`. При нарушении API возвращает 400 с `errors`.
3. **Переходы без HTTP.** `Domain/StatusRules.cs` содержит `CanTransition` и словарь разрешённых соседних статусов; тот же статус разрешён. `Unit/StatusRulesTests.cs` непосредственно проверяет метод семью наборами входных данных без HTTP и БД.
4. **404 и detail409.** Контроллер выбирает HTTP-код: например, null после `GetAsync` в `TasksController.ChangeStatus` ведёт к `NotFound()`. При запрещённом переходе текст `detail` передаётся самим контроллером в `Problem(...)`; для повторного имени проекта это делает `ProjectsController.Create`.
5. **Выбор хранилища.** В `Program.cs` `builder.Configuration["Storage"]` сравнивается с `Postgres`, после чего регистрируются соответствующие репозитории. В обоих JSON-файлах настроек выбран InMemory; фактический запуск подтверждает строка «Хранилище: в памяти», поскольку окружение может переопределить настройки.
6. **TaskService и PostgreSQL.** Сервис зависит от `ITaskRepository` и `IProjectRepository`, общих для InMemory и SQL. При смене `Storage` контейнер зависимостей предоставляет другую реализацию, а методы сервиса не меняются.

## Шесть вопросов для самопроверки из лекции 1, часть2

Это отдельные вопросы лекции `Лаба 1,3.pdf`; они дополняют шесть практических ответов выше.

1. **Frontend, backend и клиенты.** Frontend показывает интерфейс пользователю, backend выполняет логику и работает с данными. DemoApi предоставляет JSON API без собственных пользовательских страниц; обращаться к нему могут сайт, мобильное приложение, другие сервисы, Postman, Swagger и HTTP-клиенты командной строки.
2. **PUT, PATCH и201.** PUT заменяет редактируемые поля ресурса целиком: у задачи это название, описание и срок; PATCH меняет отдельную часть, например статус. Создание задачи возвращает201 Created, поскольку появился новый ресурс, а его адрес передаётся в Location;200 — общий успешный ответ без этого специального смысла создания.
3. **CreateTaskRequest вместо TaskItem.** Модель запроса содержит только разрешённые клиенту поля: projectId, title, description и dueDate. Id, исходный статус Todo и даты создания/обновления назначает сервер; при приёме TaskItem целиком клиент мог бы попытаться подменить их и обойти правила.
4. **PATCH без status.** В `ChangeStatusRequest` свойство Status имеет nullable-тип и `[Required]`; отсутствующее значение не превращается в Todo по умолчанию. `[ApiController]` автоматически вернёт400 с ошибкой валидации до выполнения `TasksController.ChangeStatus`.
5. **Выбор хранилища без изменения сервиса.** `Program.cs` читает настройку Storage и регистрирует в DI либо InMemory-, либо SQL-реализации `ITaskRepository` и `IProjectRepository`. TaskService вызывает интерфейсы, поэтому переключение конфигурации не требует менять его код.
6. **Порядок middleware метрик и ошибок.** `UseHttpMetrics()` зарегистрирован раньше `UseExceptionHandler()`, поэтому оборачивает обработчик ошибок и видит окончательный HTTP-код ответа. Когда обработчик преобразует исключение в500, этот код учитывается в HTTP-метриках приложения.

## Статистика проекта

`GET /api/projects/{id}/stats` возвращает `ProjectStats`: projectId, total, todo, inProgress, done, overdue. Контроллер сначала читает сам проект и возвращает404, если его нет; существующий пустой проект получает200 и нулевые счётчики.

`total` включает все задачи только этого проекта и равен сумме трёх статусов. `overdue` включает DueDate строго раньше текущего дня UTC при Status != Done. Срок сегодня, null, будущий срок и завершённые задачи не просрочены.

| Компонент | Реализация |
|---|---|
| `Domain/Project.cs` | Запись ProjectStats и XML-описания всех полей |
| `Data/ProjectRepository.cs` | Интерфейс IProjectRepository.GetStatsAsync и SQL-реализация |
| `Data/InMemory/InMemoryProjectRepository.cs` | LINQ внутри lock(store.Sync) |
| `Services/ProjectService.cs` | Делегирование GetStatsAsync репозиторию |
| `Controllers/ProjectsController.cs` | GetStats, маршрут, проверка существования, HTTP/XML-описания |
| `DemoApi.http` | Пример запроса статистики |
| `Integration/ProjectsApiTests.cs` | Две новые интеграционные проверки |

В SQL используются `COUNT(*) FILTER`, параметр projectId и отдельный параметр даты UTC. Это сохраняет смысл методички и устраняет зависимость `current_date` от часового пояса PostgreSQL. Значения COUNT читаются как Int64 и преобразуются в int с проверкой переполнения. SQL-код включён в реализацию и сборку; его исполнение на PostgreSQL в текущей работе не подтверждено.

Для демонстрации создайте три задачи: две Todo (одна со сроком позавчера) и одну InProgress. Ожидаемый ответ для фактического id проекта:

```json
{"projectId":1,"total":3,"todo":2,"inProgress":1,"done":0,"overdue":1}
```

В текущем тесте просроченный срок устанавливается PUT после создания. Это сохраняет проверку overdue при включённом запрете прошедшей даты во время POST; дополнительное правило касается только создания, а не изменения существующей задачи.

## Дополнительное правило и оставшаяся проверка

Запрет создания задачи со сроком в прошлом →400 отмечен в методичке как ⭐ и реализован в `TasksController.Create`. Сравнение идёт с сегодняшней датой UTC; при нарушении контроллер добавляет ошибку `DueDate` в ModelState и возвращает `ValidationProblem(ModelState)`, поэтому пояснение находится в `errors.DueDate`. Задача не создаётся. Null, сегодня и будущий срок разрешены. Явная проверка в действии выбрана для одного зависящего от времени правила POST без нового атрибута и без изменения разрешённого PUT. Проверки отсутствия записи после400 и сохранения допустимых дат включены в результат28/28.

PostgreSQL требуется проверить в лабораторной3. Dockerfile, compose, workflow CI/CD и мониторинг относятся к будущим работам и не входят в подтверждённый результат этой версии.
